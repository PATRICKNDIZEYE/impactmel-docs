# How This Manual Is Built

Every edition of this manual comes from one set of markdown chapters. Nothing is
maintained twice. This appendix is also the reference fixture for the print
pipeline: it deliberately uses every feature of the authoring contract, so a
build that renders this page correctly has exercised the whole toolchain.

## The authoring contract

A chapter is a markdown file with YAML frontmatter:

```yaml
---
title: Entering Data
chapter: 8
roles: [reporter, me_officer, org_admin]
---
```

`roles` decides which editions contain the chapter. A reader whose role is not
listed never receives the file at all — it is dropped before the PDF is
rendered, not hidden inside it.

| Field | Required | Meaning |
| --- | --- | --- |
| `title` | no | Chapter title. Falls back to the first `#` heading. |
| `chapter` | no | Sort position. Falls back to the order in `chapters.json`. |
| `roles` | yes | Which of `viewer`, `reporter`, `me_officer`, `org_admin` receive it. |

::: tip
Keep `roles` as narrow as is honest. A viewer edition that contains
administrative procedure is worse than no viewer edition, because it teaches
people to ignore the parts that do not apply to them.
:::

## Hiding part of a chapter

Whole-file filtering is often too blunt: a chapter can be broadly useful with
one procedure that only some roles should see. Wrap that part in a role fence.

```markdown
<!-- roles: me_officer, org_admin -->
### Approving submitted data
...
<!-- /roles -->
```

The fenced block below is marked for M&E officers and organisation
administrators. It is present in the complete, `me_officer` and `org_admin`
editions and absent from the `reporter` and `viewer` editions.

<!-- roles: me_officer, org_admin -->
### Approving and rejecting submitted data

Submitted values arrive in the review queue rather than going straight into
reports. As a reviewer you have two options.

1. **Approve** the submission. The value is locked and becomes visible to
   dashboards and reports.
2. **Reject** a submission back to the reporter with a comment explaining what
   needs to change. The reporter keeps their original entry and edits it.

A rejected submission is never deleted. The full history stays on the value, so
an evaluator can always see what was originally reported and what changed.
<!-- /roles -->

The next fenced block is narrower still — organisation administrators only.

<!-- roles: org_admin -->
### Rotating the organisation code

The organisation code is what new members use to request access. Rotate it after
any staff change that ends someone's employment.

Rotating the code does not remove existing members; it only invalidates the
joining code itself.
<!-- /roles -->

## Figures

A figure is a placeholder in the markdown, not markup:

```markdown
{{figure:dashboard-overview}}
```

The image path, title and descriptive caption all come from `figures.json`, so
a screenshot can be recaptured or a caption reworded without touching any
chapter. Figure numbers are never written by hand.

{{figure:figure-numbering-demo}}

Numbers are generated by CSS counters at render time, which is why they stay
correct in every edition. The viewer edition contains fewer chapters than the
complete edition, so a figure that is `12.3` in one is `7.3` in the other —
automatically, with no source change.

## Branding

Colours, organisation name, logo and the "powered by" line are build arguments.
The same chapters produce an ImpactMEL-branded manual for internal use and a
client-branded manual for a tenant who wants the platform in the background.
